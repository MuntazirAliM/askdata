# Ask Your Data: multi-location business agent

A natural-language analytics assistant for a fictional restaurant group with five UK locations.
An owner can ask questions about every site. A manager can only ever see their own.

This repository is being built in phases. **Phases 1 to 5 are here: database, data, security, a validated
SQL tool and the question-answering agent.** The interface, evaluation and deployment follow.

All data is fictional and generated by `app/generate_data.py`.

## What is in the database

| Object | What it holds |
|---|---|
| `locations`, `products` | 5 sites, 20 menu items |
| `orders`, `order_items` | about 224,000 orders and 644,000 items over 12 months |
| `daily_sales`, `product_sales` | Reporting views with documented columns. The agent queries only these. |
| `app_users` | Who can log in and which database role they use |

The data has realistic weekday and seasonal patterns plus four planted stories (a staffing dip, a
discount week, a delivery shift and a refund spike). They are listed in `data/planted_stories.md` after
setup, and they become the answer key when the agent is evaluated.

## Security design

The agent writes SQL, so the database must stay safe even if the agent is tricked.

- One real login role per person type: `askdata_owner` and `askdata_mgr_1` to `askdata_mgr_5`.
- Row-level security: a manager's connection can only see rows for their own location.
- Reporting views use `security_invoker`, so the same rules apply through the views.
- Roles are read-only, have a 5 second statement timeout, and cannot read `app_users`.
- The application picks the role when it opens the connection. There is no setting the agent's SQL can
  change to widen its own access.

`python app/check_security.py` tries to break these rules and prints a pass or fail for each.

## How the agent answers a question

A fixed pipeline, so every answer can be inspected (`python app/ask.py --trace "..."`):

1. **Write**: the model writes one SELECT query from the question and the documented schema.
2. **Check**: `app/sqlguard.py` rejects anything that is not a plain read of the allowed views, uses a
   function outside a short safe list, has comments, stacked statements or `SELECT ... INTO`.
3. **Run**: the query runs as that person's own database role, so row-level security applies.
4. **Repair**: if the guard or the database rejects it, the error goes back to the model (up to 3 tries).
5. **Explain**: the model writes a short answer from the result rows only.
6. **Verify**: `app/grounding.py` checks every number in the answer against the result. One rewrite is
   requested for any figure that is not there, and a warning is shown if it still is not.

The guard is a second layer. Even if it were bypassed, the database role could still only read the
reporting views and, for a manager, only their own location.

The model is swappable through `.env` (Ollama locally, Groq for the hosted demo). The agent code is the same.

```
ollama pull qwen2.5:7b
python app/ask.py "Which location sold the most last week?"
python app/ask.py --as manager:3 --trace "How did we do this month?"
python app/ask.py                       # interactive chat
```

```
python -m unittest discover -s tests -p "test_*.py"   # guard and number-check unit tests
python tests/smoke_agent.py                           # whole pipeline on the real database, scripted model
```

## Run it (Windows, PowerShell)

Needs PostgreSQL 15 or newer, Python 3.10 or newer, and an empty database called `shops`.

```
conda create -n askdata python=3.11 -y
conda activate askdata
pip install -r requirements.txt
copy .env.example .env
```

Edit `.env`: set `PGPASSWORD` to your postgres password and choose any `AGENT_PASSWORD`. Then:

```
python app/setup_db.py
python app/check_security.py
```

`setup_db.py` finds `psql` automatically in the usual install folders. If it cannot, set `PSQL_PATH` in `.env`.
